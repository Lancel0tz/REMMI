## Your retrieval tool (ALL discovery AND detail lookup goes through it)

Search — accepts SEVERAL queries in one call; batch your phrasings and sub-questions:
```
python3 memory/search.py "query one" "query two" [--top-k 12] [--start YYYY-MM-DD] [--end YYYY-MM-DD] [--city <substr>] [--type image|video|email|any]
```
Inspect records by id — one compact line each (time, city, location, caption, ocr):
```
python3 memory/search.py --show id1,id2,id3,...
```
`--show ... --full` prints complete records (full captions, full email bodies).

Event layer — the whole corpus is pre-organised into ~392 chronological
events/trips. Search events, then list an event's members:
```
python3 memory/search.py --events "trip to Glasgow" "Portugal visit"
python3 memory/search.py --event P0142
```
An event line shows: event_id | kind | date range | city | item/email counts | title.
`--event <id>` lists every member item (compact) and the event's email ids.

## THREE KINDS OF QUESTIONS — THREE KINDS OF ANSWERS (CRITICAL)

A) RECALL/LIST questions ("find all the images/videos...", "which memory items...")
   → answer = the memory item IDs ONLY, comma-separated.
B) NUMBER questions ("how many...", "how much did I pay/spend...", "how long...")
   → answer = the NUMBER (with unit/currency) and NOTHING ELSE. No breakdown,
   no explanation, no date list. Compute carefully from the evidence, then
   output just the final figure (e.g. "10 days", "£190", "434.97").
C) EVERYTHING ELSE — "which hotels / cities / restaurant", "when did I...",
   "why did I like..." → answer = NATURAL LANGUAGE with the actual names,
   dates, and reasons. NEVER answer these with item ids.

For type B and C you MUST run `--show <finalist ids> --full` before answering:
names, prices, and reasons live in the full captions and email bodies, not in
the truncated compact lines. Full records are cheap (~0.5KB).

## Workflow: search -> organise -> answer (BE THOROUGH — completeness beats brevity)

1. ANALYZE the question: type (A, B or C above), dates, places, entities, activities, modalities.
2. PICK THE LAYER, then SEARCH:
   - Questions about trips, visits, stays, "how many nights/days/times",
     periods, or whole outings → START WITH THE EVENT LAYER (`--events`).
     Event date ranges give you visit boundaries and counts directly;
     `--event <id>` gives the complete member list (great for recall coverage).
   - Questions about a specific object/moment/detail → item search as usual.
   Use both layers when unsure — they are cheap. Batch queries and filters. Then CHECK COVERAGE: rephrase and
   search again for aspects the first pass may have missed (synonyms, nearby
   dates, related events, emails as well as photos/videos). Run as many search
   rounds as the question needs — recall questions need EVERY matching item,
   multi-part questions need every part covered.
3. INSPECT the plausible ids with --show (batched). For type-B/C questions,
   follow up with `--full` on the finalists to extract names/details/reasons.
4. ORGANISE: write `timeline.md` — one line per relevant item:
   `<item_id> | <timestamp> | <city> | <key facts for the answer>`, grouped
   chronologically, related emails merged in. If it looks incomplete, return to step 2.
5. ANSWER from the timeline in the format the question type demands
   (ids for A; bare number for B; names/dates/reasons in prose for C).

Thoroughness rule: do not answer "Unknown" or give a partial answer until you
have tried at least two differently-phrased search rounds for each aspect of
the question, and (for type B/C) inspected the finalists with --full.

## Memory item IDs (for recall/list questions)

- Image/video ID = filename without extension from `image_path` / `video_path`.
  Example: `.../20220507_150929.jpg` → `20220507_150929`
- Email ID = the `id` field in `emails.json` (e.g., `email202201010001`).
- The ids printed by search.py are exactly these IDs.
